# Советчик по продвижению товаров

[![tests](https://github.com/eegorovag-wq/ai-promo-advisor/actions/workflows/tests.yml/badge.svg)](https://github.com/eegorovag-wq/ai-promo-advisor/actions/workflows/tests.yml)

Небольшой рабочий сервис для интернет-магазина: он подсказывает менеджеру, **какой товар стоит продвигать прямо сейчас**, объясняет выбор на данных магазина, готовит черновик публикации с помощью языковой модели — и не даёт ничего опубликовать без согласования человеком.

Проект сделан как портфолио-кейс по внедрению ИИ в рабочий процесс: от бизнес-задачи до измеримого качества и честно названных ограничений. Данные в репозитории синтетические.

---

## Задача

В магазине подарков менеджер каждую неделю решает, что показать в Telegram и MAX. Решение принимается на глаз: обычно продвигают то, что вспомнили, или то, что и так хорошо продаётся. Из-за этого:

- рекламируются товары, которых нет на складе;
- в ленту попадает одно и то же;
- продвигаются позиции с низкой прибылью;
- сезонные товары вспоминают поздно.

## Где здесь уместен ИИ, а где нет

Прежде чем что-то внедрять, задача разделена на две части.

**Языковой модели отдано то, что плохо формализуется:**

- человеческая формулировка объяснения, почему выбран этот товар;
- текст публикации в брендовом тоне.

**Модели не отдано ничего из этого:**

| Задача | Кто решает | Почему |
|---|---|---|
| Какой товар продвигать | Код | Решение должно быть воспроизводимым и проверяемым; модель объяснит любое число, но подтвердить его нечем |
| Цена, скидка, остаток | Человек в своей системе | Цена ошибки — деньги и репутация |
| Публиковать или нет | Человек | Публикация необратима |
| Расчёт показателей | Код | Выдуманная цифра в рекламе хуже отсутствия рекламы |

Признак, по которому делили: **можно ли проверить результат формулой**. Если да — это работа кода. Если нет и ошибка не фатальна — это работа модели под надзором человека.

## Решение

```
данные магазина (остаток, продажи, маржа, публикации, повод)
        ↓
детерминированный расчёт приоритета      ← обычный код, покрыт тестами
        ↓
языковая модель: объяснение + текст      ← строгий JSON, проверяется кодом
        ↓
согласование человеком                   ← без него публикации нет
        ↓
публикация и журнал действий
```

## Как запустить

Нужен только Python 3.11+. Никаких зависимостей, установка не требуется.

```bash
python -m promo_advisor recommend --today 2026-12-20
python -m promo_advisor draft p01 --channel telegram --audience "постоянные клиенты"
python -m promo_advisor queue
python -m promo_advisor approve 1 --actor "Елена"
python -m promo_advisor publish 1 --actor "Елена" --at 2026-12-20T12:00
python -m promo_advisor evaluate
python -m unittest discover -s tests -t .
```

По умолчанию работает встроенная заглушка модели: сеть и ключи не нужны, результат воспроизводим. Реальная модель подключается переменными окружения, ключ в репозиторий не попадает:

PowerShell:

```powershell
$env:PROMO_LLM_API_KEY="..."
$env:PROMO_LLM_BASE_URL="https://api.openai.com/v1"
$env:PROMO_LLM_MODEL="gpt-4o-mini"
```

Bash:

```bash
export PROMO_LLM_API_KEY="..."
export PROMO_LLM_BASE_URL="https://api.openai.com/v1"
export PROMO_LLM_MODEL="gpt-4o-mini"
```

Пример вывода:

```
100/100  Свеча «Тихий вечер»  [p01]
        +25  Остаток 40 шт.
        +25  Маржа 65% (970 ₽)
        +20  За 30 дней продано 3 шт.
        +20  За 30 дней не публиковался
        +12  До повода «Новый год» 11 дн.
```

## Что внутри

| Файл | Зачем |
|---|---|
| `promo_advisor/scoring.py` | приоритет продвижения: остаток, маржа, продажи, частота публикаций, близость повода |
| `promo_advisor/guardrails.py` | запреты: общий стоп, обязательное согласование, потолок скидки, тихие часы, запрещённые формулировки |
| `promo_advisor/llm.py` | строгий контракт с моделью, разбор и проверка ответа, заглушка без сети |
| `promo_advisor/text_quality.py` | проверка готового текста правилами, включая поиск выдуманных чисел |
| `promo_advisor/workflow.py` | черновик → согласование → публикация, журнал действий в SQLite |
| `promo_advisor/evaluate.py` | прогон размеченных сценариев и сравнение версий логики и промпта |
| `data/` | синтетический каталог, календарь поводов, 24 сценария с экспертной разметкой |
| `tests/` | 37 тестов, включая регрессии Windows CLI и запрета обхода согласования |

Тесты автоматически запускаются в GitHub Actions на Windows и Linux с Python 3.11 и 3.14.

## Внутренняя acceptance-проверка

Проверяются обе половины работы агента: выбор товара и текст публикации. Это регрессионная проверка согласованности правил, а не точность на независимой выборке и не оценка влияния на продажи.

**Выбор товара** — 24 синтетических сценария, размеченных вручную: для каждого указано, какой товар должен быть первым и почему.

| Версия | Верных решений | Доля |
|---|---|---|
| v1 — остаток, продажи, частота публикаций | 7 из 24 | 29 % |
| v2 — добавлены маржа, сезонность и явные отказы | 21 из 24 | 88 % |

**Текст публикации** — 8 черновиков, проверка правилами: запрещённые формулировки, давление срочностью, длина, упоминание товара, призыв к действию и числа, которых не было во входных данных.

| Версия промпта | Текстов без нарушений | Чаще всего нарушалось |
|---|---|---|
| v1 — без ограничений | 0 из 8 | рекламные штампы, срочность, выдуманная скидка |
| v2 — текущий | 8 из 8 | — |

Подробный разбор, включая три сценария, которые v2 **не проходит**, — в [docs/EVALUATION.md](docs/EVALUATION.md).

## План внедрения и мониторинга

Как этот прототип доводится до работы с живыми покупателями:

1. **Тихий режим, 2 недели.** Агент считает приоритет и готовит черновики, менеджер работает как раньше. Сравниваем: совпадает ли его выбор с подсказкой. Цель — увидеть, где система ошибается на реальном каталоге, до того как она на что-то влияет.
2. **Ручной режим.** Менеджер берёт подсказку в работу, но каждый текст правит сам. Считаем долю черновиков, ушедших в публикацию без правок, и причины отказов — это прямой материал для правки промпта.
3. **A/B на живом магазине.** Половина публикаций по подсказке, половина по решению менеджера. Сравниваем заказы по товару за 7 дней после публикации. Без этого шага говорить о влиянии на выручку нельзя.
4. **Автоматизация после согласования.** Можно автоматизировать отправку уже согласованного человеком материала и оставить общий стоп под рукой. Само обязательное согласование не отключается.

**Что отслеживать постоянно:** доля отклонённых черновиков и причины, число сработавших запретов, доля публикаций в тихие часы (должна быть нулевой), отказы модели отвечать нужной структурой, расхождение между подсказкой и решением менеджера. Рост расхождения — сигнал, что данные или веса устарели.

## Ограничения

Честно о том, чего система не умеет:

1. **Это приоритет, а не прогноз.** Балл показывает, что стоит проверить человеку. Доказанной связи «публикация → дополнительные продажи» в данных нет, поэтому ожидаемая прибыль не считается и так не называется.
2. **Нет данных о поставках.** Товар, который приедет завтра, система отвергнет как отсутствующий (сценарий S13).
3. **Вес сезонности подобран вручную** и в споре с маржой проигрывает (сценарий S14). Нужны исторические данные по сезонам.
4. **Формула маржи упрощена.** Она учитывает долю и сумму `цена − себестоимость`, но не комиссии, налоги, доставку и стоимость привлечения клиента. Поэтому балл нельзя трактовать как чистую прибыль или EV; конфликт доли и суммы виден в сценарии S23.
5. **Сценарии размечены автором правил.** Это проверка логики, а не независимый замер. Следующий шаг — разметка вторым человеком и сверка.
6. **Канал публикации — заглушка.** Отправка в Telegram и MAX не реализована, система доходит до «опубликовано» и фиксирует это в журнале.
