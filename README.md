# Советчик по продвижению товаров

Небольшой рабочий сервис для интернет-магазина: он подсказывает менеджеру, **какой товар стоит продвигать прямо сейчас**, объясняет выбор на данных магазина, готовит черновик публикации с помощью языковой модели — и не даёт ничего опубликовать без согласования человеком.

Проект сделан как портфолио-кейс по внедрению ИИ в рабочий процесс: от бизнес-задачи до измеримого качества и честно названных ограничений. Данные в репозитории синтетические.

---

## Задача

В магазине подарков менеджер каждую неделю решает, что показать в Telegram и MAX. Решение принимается на глаз: обычно продвигают то, что вспомнили, или то, что и так хорошо продаётся. Из-за этого:

- рекламируются товары, которых нет на складе;
- в ленту попадает одно и то же;
- продвигаются позиции с низкой прибылью;
- сезонные товары вспоминают поздно.

## Решение

```
данные магазина (остаток, продажи, маржа, публикации, повод)
        ↓
детерминированный расчёт приоритета      ← обычный код, покрыт тестами
        ↓
языковая модель: объяснение + текст      ← строгий JSON, проверяется кодом
        ↓
согласование человеком                   ← без него публикации нет
        ↓
публикация и журнал действий
```

**Ключевое решение: приоритет считает код, а не модель.** Языковая модель убедительно объяснит любое число, но проверить его нельзя. Здесь каждый балл виден, воспроизводится и покрыт тестами, а модели оставлено то, что она делает хорошо: человеческая формулировка.

Модель не может: менять цену, назначать скидку, трогать остатки, публиковать без согласования, придумывать показатели.

## Как запустить

Нужен только Python 3.11+. Никаких зависимостей, установка не требуется.

```bash
python -m promo_advisor recommend --today 2026-12-20
python -m promo_advisor draft p01 --channel telegram --audience "постоянные клиенты"
python -m promo_advisor queue
python -m promo_advisor approve 1 --actor "Елена"
python -m promo_advisor publish 1 --actor "Елена" --at 2026-12-20T12:00
python -m promo_advisor evaluate
python -m unittest discover -s tests -t .
```

По умолчанию работает встроенная заглушка модели: сеть и ключи не нужны, результат воспроизводим. Реальная модель подключается переменными окружения, ключ в репозиторий не попадает:

```bash
PROMO_LLM_API_KEY=...  PROMO_LLM_BASE_URL=https://api.openai.com/v1  PROMO_LLM_MODEL=gpt-4o-mini
```

Пример вывода:

```
100/100  Свеча «Тихий вечер»  [p01]
        +25  Остаток 40 шт.
        +25  Маржа 65% (970 ₽)
        +20  За 30 дней продано 3 шт.
        +20  За 30 дней не публиковался
        +12  До повода «Новый год» 11 дн.
```

## Что внутри

| Файл | Зачем |
|---|---|
| `promo_advisor/scoring.py` | приоритет продвижения: остаток, маржа, продажи, частота публикаций, близость повода |
| `promo_advisor/guardrails.py` | запреты: общий стоп, обязательное согласование, потолок скидки, тихие часы, запрещённые формулировки |
| `promo_advisor/llm.py` | строгий контракт с моделью, разбор и проверка ответа, заглушка без сети |
| `promo_advisor/workflow.py` | черновик → согласование → публикация, журнал действий в SQLite |
| `promo_advisor/evaluate.py` | прогон размеченных сценариев и сравнение версий логики |
| `data/` | синтетический каталог, календарь поводов, 14 сценариев с экспертной разметкой |
| `tests/` | 28 тестов |

## Качество решения

Проверка на 14 сценариях, размеченных вручную: для каждого указано, какой товар должен быть первым и почему.

| Версия | Верных решений | Доля |
|---|---|---|
| v1 — остаток, продажи, частота публикаций | 3 из 14 | 21 % |
| v2 — добавлены маржа, сезонность и явные отказы | 12 из 14 | 86 % |

Что исправила вторая версия: рекомендации товаров без остатка, продвижение позиций с ценой ниже себестоимости, игнорирование прибыли, порядок при равных баллах по алфавиту вместо денег, молчание вместо честного пустого ответа.

Подробный разбор, включая два сценария, которые v2 **не проходит**, — в [docs/EVALUATION.md](docs/EVALUATION.md).

## Ограничения

Честно о том, чего система не умеет:

1. **Это приоритет, а не прогноз.** Балл показывает, что стоит проверить человеку. Доказанной связи «публикация → дополнительные продажи» в данных нет, поэтому ожидаемая прибыль не считается и так не называется.
2. **Нет данных о поставках.** Товар, который приедет завтра, система отвергнет как отсутствующий (сценарий S13).
3. **Вес сезонности подобран вручную** и в споре с маржой проигрывает (сценарий S14). Нужны исторические данные по сезонам.
4. **Сценарии размечены автором правил.** Это проверка логики, а не независимый замер. Следующий шаг — разметка вторым человеком и сверка.
5. **Канал публикации — заглушка.** Отправка в Telegram и MAX не реализована, система доходит до «опубликовано» и фиксирует это в журнале.
